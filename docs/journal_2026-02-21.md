### 8. Ring 4 diagnosis: interlocked blocks and DT normalization bug

**The interlocking problem:** All 7 blocks at ring 4 (innermost ring) share the **same X band** (~740-1090px, 350px wide) in the depth map. They are staggered in the Y (angular) direction, forming an interlocking jigsaw pattern:

```
Y-position |  K  | B1  | A1  | A2  | A3  | A4  | B2  |
     0      |     |     |     | === |   = |     |     |
   500      |     |     | === | === | === |     |     |
  1000      |     |     | === |     |     | === |     |
  1500      |     | === |     |     |     | === | === |
  2000      | === | === |     |     |     |     | === |
  2500      | === | === |     |     |     |     | === |
  3000      |     | === |     |     |     | === | === |
  3500      |     |     | === |     |     | === |     |
  4000      |     |     | === | === | === |     |     |
```

**The DT normalization bug:** When the distance-transform logits are normalized (`dt / max_dt`), tall narrow templates (like B1: 392px wide × 2287px tall) produce a flat 1.0 zone across their entire center line, because `max_dt` is limited by the narrow width (196px). This means B1 claims logit=1.0 over a 1895px vertical strip, overwriting K (37.2% accuracy) and B2 (39.5% accuracy) at their own centers.

Mathematically, at K's center pixel:
- K's normalized DT = 0.986 (its center is 208px from the nearest edge, max_dt = 211px)
- B1's normalized DT = 1.000 (its center is >196px from all edges, max_dt = 196px)
- B1 wins → K's pixels get labeled as B1 → K accuracy = 37%

**Attempted fixes:**
- Absolute (un-normalized) DT: marginal improvement (+1% overall, K 37%→40%) but caused regressions at other rings (B1 ring 2: 53.7%→12.2%). Reverted.
- Adding A4 back: its massive template (dy_neg=11065mm) overwrites B1 (81.5%→13.4%) and B2 (40%→0%). Removed.

**Working fix:** GT pixel mask override for ring 4. Instead of rectangular templates, use the actual GT pixel labels (`gt_label_ring4.npy`) which capture the true interlocking block shapes. This bypasses the DT competition entirely for ring 4.

**Result:** Ring 4 accuracy: 100% (from 33.8%). Overall no-wrap mIoU: **0.7773** (from 0.7073).

### 10. Angular boundary masks: solving interlocking without GT pixel masks

**Problem:** Rectangular templates fail at interlocking rings because the DT normalization bug allows tall narrow blocks to overwrite smaller blocks. GT pixel masks solve this perfectly but require ground truth.

**Solution:** Replace DT-based conflict resolution with **angular boundary partitioning**. At each ring, sort block centroids by Y, place boundaries between adjacent blocks, and assign each pixel to the block whose angular slice contains it. This produces non-overlapping slices — no DT competition needed.

**Implementation:**
- `compute_angular_boundaries()`: computes per-ring angular slices from block centroids + tunable boundary fractions
- `load_gt_angular_boundaries()`: loads pre-computed GT-optimal boundaries from `gt_angular_boundaries.json`
- **Hybrid aggregation**: angular boundaries decide *which* block owns a pixel; template masks decide *whether* the pixel is block or background (excluding grooves)
- New params in `parameters_sam.json`: `use_angular_boundaries`, `use_gt_boundaries`, `boundary_fraction_bk/ba/aa`

**GT-optimal boundary fractions (reverse-engineered from GT edge pixels):**

| Pair type | Mean fraction | Std | Range | Notes |
|-----------|---------------|-----|-------|-------|
| A-A | 0.496 | 0.058 | 0.36-0.56 | Nearly midpoint |
| A-B | 0.490 | 0.049 | 0.40-0.57 | Nearly midpoint |
| B-K | 0.482 | 0.247 | 0.21-0.77 | Highly variable — key BO target |

**Results:**

| Configuration | mIoU (no-wrap) | Notes |
|---------------|----------------|-------|
| Shared rect templates + DT (baseline) | 0.578 | Original |
| Per-instance rect templates + DT | 0.707 | GT-derived mask sizes |
| + Ring 4 GT pixel mask override | 0.777 | Ring 4 = 100% |
| Angular bounds + template (frac=0.5) | 0.749 | 3 BO-tunable params |
| Angular bounds + template (GT-mean frac) | 0.748 | GT-mean of above fractions |
| **Angular bounds + template (GT-optimal/ring)** | **0.809** | Per-ring optimal boundaries |
| Ceiling (pixel-majority) | 0.993 | Theoretical max |

**Key finding:** The B-K boundary fraction varies from 0.21 to 0.77 across rings. A single global fraction cannot capture this — the gap from 0.749 (parameterized) to 0.809 (GT-optimal) is entirely due to per-ring B-K variation. The solution: replace the fraction model with a **half-extent model** (see Plan for Next Session).

## Plan for Next Session

### Priority 1: Half-extent boundary model (replace fractions)

The fraction model (`cy1 + f * (cy2 - cy1)`) mixes block sizes with gap sizes, making the B-K boundary unpredictable. Replace with a **half-extent model**:

```
boundary = (centroid_left + half_left + centroid_right - half_right) / 2
```

This places the boundary at the midpoint of the gap between block edges, using physically meaningful parameters:

| Parameter | GT value | Std | BO range |
|-----------|----------|-----|----------|
| `k_angular_half` | 149px | 1.3px | [140, 160] |
| `b_angular_half` | 376px | 14px | [330, 420] |
| `a_angular_half` | 349px | 41px | [260, 400] |

3 BO-tunable parameters, physically grounded, replace the 3 fraction parameters. Predicted mean boundary error: ~25px (vs ~61px for fractions).

### Priority 2: Stagger geometry for centroid prediction

Currently using GT centroids. For deployment, non-K centroids must be derived from K positions. Parameterize the staggering geometry:

| Parameter | Description | BO-tunable |
|-----------|-------------|------------|
| `b_offset_magnitude` | Angular distance from K to B1/B2 (~500px) | Yes |
| `stagger_shift` | Per-ring rotation of the block pattern | Yes |
| Phase detection | Which rings flip B1/B2 sides | Derived from data |

With these ~2-3 params + K detection (already BO-tuned, ~14 params), all non-K centroids can be predicted.

### Priority 3: Wrap-around blocks (8 blocks)

8 blocks span the periodic Y boundary of the depth map. No single unfolding can avoid all wraps — the stagger rotation places grooves at different Y positions per ring, so any seam cuts through at least one block per ring. Three approaches to explore, in order of simplicity:

**Approach A: Periodic Y crop windows (extend existing X-wrap logic)**

The code already handles X-axis wrap-around in `crop_image_and_mask_logits`: when a crop extends past the left/right edge, it grabs pixels from the opposite side and concatenates them. Apply the same logic to Y:

- When `cy - crop_height/2 < 0`, grab bottom rows of the image and prepend them above
- When `cy + crop_height/2 > img_height`, grab top rows and append them below
- Template masks and angular boundaries already handle Y wrap (y_start > y_end)
- Minimal code change — only `crop_image_and_mask_logits` and the aggregation back-projection

**Approach B: Double-height depth map**

Duplicate the depth map vertically: stack the image on top of itself to create a 2x-height image (9424px for tunnel 5-1). Wrap-around blocks that were split across top/bottom now appear contiguous in the middle. Process normally, then project back using `Y % img_height`.

- Simple conceptually — no changes to crop/template/boundary logic
- Doubles the image size and processing time
- Pixels near the seam get processed twice (once in the top copy, once in the bottom) — need deduplication
- SAM crops near the middle of the doubled image see the "true" continuous block

**Approach C: Per-ring unfolding (different cut per ring)**

For each ring, choose a cut position that falls in a groove (gap between blocks), so no block at that ring wraps. Each ring gets its own depth map strip:

- Eliminates wrap-around entirely — every block is contiguous in its ring's strip
- Requires knowing groove positions per ring (from detection or GT)
- Breaks the shared depth map assumption — SAM would process per-ring strips instead of one image
- More complex pipeline but the cleanest geometric solution
- The groove positions are computable from angular boundaries (the boundary between adjacent blocks IS the groove)

**Evaluation plan:** Try A first (simplest). If SAM crops across the Y seam produce poor masks (e.g., color discontinuity at the seam), try B. If neither works well, implement C as the definitive solution.

### Priority 4: Template mask refinement

The remaining BG IoU gap (0.62) comes from template masks being too large at block edges. Tighter masks (from half-extents or GT pixel masks for all rings) would improve this.

## Reflection (Updated)

Today's breakthrough: **angular boundary partitioning** replaces the broken DT competition as the conflict resolution mechanism. The progression 0.578 → 0.707 → 0.777 → **0.809** was driven entirely by GT-reverse-engineering: first fixing preprocessing coverage, then per-instance template sizes, then per-ring angular boundaries.

The remaining gap to the 0.993 ceiling is now well-characterized:
- **Boundary placement accuracy** (0.06 mIoU): solvable with the half-extent model + BO
- **Template mask over-assignment** (0.08 mIoU): solvable with tighter masks derived from half-extents
- **Wrap-around blocks**: only affects full mIoU, deferred

The key architectural insight: **separation of concerns**. Angular boundaries handle inter-block conflict resolution (which block owns this pixel?). Template masks handle block-vs-background classification (is this pixel surface or groove?). DT was trying to do both at once and failing at the first task. By separating them, each mechanism does what it's good at.

The half-extent model is the natural next step: 3 physically grounded BO parameters that predict per-ring boundaries from centroids alone. Combined with stagger geometry (~3 more params) for centroid prediction from K-only detection, the full pipeline becomes: 14 Hough params + 3 stagger params + 3 half-extent params = ~20 BO-tunable parameters for end-to-end segmentation without GT.

### Root Cause: Not a Crop Problem

The wrap failure is NOT caused by how the crop is assembled (periodic vs doubled vs unfolded). It's caused by:

1. **Angular boundary mismatch**: The GT angular boundaries for wrap blocks have `y_start > y_end` (e.g., A3 at ring 6: y_start=4496, y_end=526). The y_lookup correctly handles this wrapping case, but the template mask geometry is computed in a non-wrapping coordinate system, causing the intersection of (template AND angular_match) to be nearly empty for blocks that span the Y boundary.

2. **Template mask misalignment**: The template mask is generated relative to the crop centre. For wrap blocks whose true centroid is near Y=0 or Y=img_h, the template extends in both directions but the crop is clipped at the image boundary (Y=0 or Y=4712). The template covers the wrong region of the block.

### Key Insight

The three approaches would produce **different results only when using SAM's actual vision model** (`use_template_fallback=false`), where the quality of the crop image matters:
- **A** gives a stitched image (potential seam discontinuity)
- **B** gives a continuous doubled image (no seam, but 2x memory)
- **C** gives a naturally continuous rolled image (cleanest, no waste)

For template-fallback mode, the fix must happen at the **angular boundary + template mask level**: the wrap block's template and angular assignment must be computed in a coordinate system where the block doesn't wrap. This is exactly what Approach C's per-ring unfolding provides — it just needs to be applied to the aggregation logic, not just the crop.

### Revised Plan

Approach C has the right architecture: per-ring coordinate shifting eliminates wrap at a fundamental level. But it must be applied consistently to:
1. **Block centroids** (done — shifted by cut_y)
2. **Angular boundaries** (done — shifted slices)
3. **Template masks** (done — generated in shifted space)
4. **Aggregation back-projection** (done — un-shifted per row)

The remaining issue is that the template mask instance params (dy_neg, dy_pos) for wrap blocks are still computed from the original (wrapped) coordinate system, giving very large/incorrect values. These need to be recomputed in the per-ring shifted space.

#### Key Conclusions

1. **Template masks vastly outperform SAM vision model** (0.74 vs 0.50 overall). The depth map lacks sufficient visual contrast for SAM to reliably segment blocks. SAM over-predicts mask area by 30-45%, causing massive FP.

2. **Among template approaches, A and B are tied (~0.762), C trails at 0.750.** Approach A (Periodic Y Crop) has a slight edge on wrap blocks (0.614 vs 0.602).

3. **SAM vision model is counterproductive for this task.** Even for wrap blocks where crop quality matters, template still wins (0.61 vs 0.54).

4. **The geometric template + angular boundary approach is the right strategy.** Future improvements should focus on:
   - Better template parameterization (per-instance GT-derived params already help)
   - Angular boundary refinement (BO-tunable boundary fractions)
   - Ring 4 interlocking resolution (currently uses GT override)
