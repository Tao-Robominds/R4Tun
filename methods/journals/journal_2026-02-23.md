## Objective

Test whether the best GT-tuned geometric segmentation parameters (trial 152, achieved 0.774 mIoU with GT segments) can improve performance when used with non-GT K positions (BO K and Multisource K).

---

**Baseline:** BO K positions + Current geometric params = **0.305 mIoU** (best non-GT result)

**Previous work:**
- Multisource K Y detection achieved mean |dY| = 900px (vs BO K's 962px), but end-to-end mIoU was worse (0.217 vs 0.305)
- Trial 152 geometric params achieved 0.774 mIoU with GT segments (best from GT-based segmentation BO)
- Hypothesis: Trial 152 params might better tolerate K Y errors and improve Multisource K performance

## Detection Pipeline BO-Tunability (Important)

All detection components that affect segment positions are BO-tunable:

1. **K detection params** (groove-pair thresholds, DBSCAN eps, angle ranges, etc.): Already BO-tuned in the existing pipeline. The Feb 19 journal shows K-only BO achieving ~56 px mean drift on 5-1.

2. **Per-ring offsets** (6 offsets per ring = 42D total): BO-tuned via ring-by-ring decomposition (7 independent 6D BO runs). Feb 19 journal: reduced mean drift from 948 px to 317 px on 5-1 using the `segments_ring` objective in `run_detection_bo.py`.

3. **Walking order**: Implicitly BO-tunable through the **sign** of the offsets. If BO gives `B1_offset = -460` (negative), B1 goes "backward" from K; if `+518` (positive), B1 goes "forward". No separate categorical parameter is needed — BO discovers the correct direction naturally within the `[-2400, +2400]` search range.

## K detection regulator overhaul + BO (locked results)

**Objective:** Fix regulator so Y improves overall; use BO to tune regulator and detection jointly.

**Root cause:** Heuristic regulator used a median "universal gap" (302 px) polluted by non-groove pairs; true groove gap at good rings is ~148 px (K_HEIGHT_PX/2). Wrong gap caused wrong pos/neg pair choice and worse Y at several rings.

**Implementation:**

1. **Regulator simplified** (`p4tun/4-1-1_geo_k_detection.py`): Replaced heuristic with 4 BO-tunable params:
   - `reg_target_gap`: expected pos/neg gap (default K_HEIGHT_PX/2)
   - `reg_gap_tolerance`: fractional tolerance around target
   - `reg_blend_weight`: blend line-based Y vs detection (0–1)
   - `reg_max_det_line_dist`: if line Y too far from detection, use detection only  
   Pair selection: among (pos, neg) pairs with gap within tolerance of target, pick midpoint closest to detected Y.

2. **BO search space** (`p4tun/bo/k_detection_bo.py`): Added `_get_k_height_px()`, `_regulator_dims()`; all 7 methods append the 4 regulator dimensions (tunnel-dependent bounds).

3. **Phase A:** 5-trial verification across all 7 methods (dims 10–16). All passed.

4. **Phase B:** 200-trial BO for dbscan, banded, edge_projection.

## SAM Complex Analysis (4-2_sam_complex.py)

Comprehensive analysis of why SAM-based segmentation achieves only **0.19 mIoU** with GT positions, compared to geometric methods at **0.77-0.99 mIoU**.

### Problem List

| # | Problem | Impact | Fixable? |
|---|---------|--------|----------|
| 1 | SAM can't segment depth maps | Fundamental -- masks unreliable | No (SAM limitation) |
| 2 | Hardcoded prompt point positions | Points misaligned with BO-tuned dimensions | Yes (parameterize) |
| 3 | B1/B2 template partially hardcoded | Template shape doesn't match tuned params | Yes (load from JSON) |
| 4 | Shared template sizes for all instances | Same mask for different-sized blocks | Yes (per-instance sizing) |
| 5 | y_bounds filter [4200, 13100] hardcoded | Strips negative points near image edges | Yes (compute from image) |
| 6 | Ring 5 GT blocks overlap in Y | 3 blocks at Y~1339 -- SAM can't separate | Structural (data) |
| 7 | SAM masks too conservative | Large unlabeled gaps between blocks | Partially (template fallback) |
| 8 | No background tiling | Unlabeled pixels stay pred=0 | Yes (template fill) |
| 9 | pred update filter [0, 7] | Minor -- locks out previously-labeled points | Yes (widen filter) |

### Problem Details

**Problem 1 (Fundamental):** SAM was trained on natural RGB images. A tunnel depth map is grayscale with subtle groove textures as the only block boundary signal. SAM's vision encoder cannot reliably distinguish one block from another -- they all look like flat gray surfaces. Even with perfect GT positions, SAM gives terrible masks.

**Problem 2:** `generate_prompt_points` (line 149-293) has all coordinates as literal numbers. Even though `SAM_PARAMS` loads BO-tuned values (K_height=1000, AB_height=3376.85, segment_width=1238.79), the prompt point grid is stuck at default values (K_height=1079.92, AB_height=3239.77). Prompt points are misaligned with actual BO-tuned block dimensions by ~137 mm vertically for A/B blocks.

**Problem 3:** `generate_template_mask` (line 123-147) reads `SAM_PARAMS['ab_mask_width']` and `SAM_PARAMS['ab_mask_height']` for A-blocks, but B1/B2 slant values (1540.69 and 1699.08) are hardcoded directly, not loaded from JSON.

**Problem 4:** Template mask dimensions are per-type, identical for every instance. A-blocks use the same rectangle for all 7 rings. But actual block sizes vary significantly -- ring 5 and 6 blocks are compressed.

**Problem 5:** Line 272 uses hardcoded `y_bounds = [4200, 13100]` mm. For 4-1 (image height 2778 px = 13890 mm), this strips negative prompt points at absolute Y < 840 px or > 2620 px. GT blocks exist at Y as low as 267 px and as high as 2498 px.

**Problem 6:** From `all_segments_gt.csv`, ring 5 has B2 (Y=1339.1), A1 (Y=1340.3), and A2 (Y=1339.3) -- three blocks at essentially the same Y coordinate. Their SAM crops overlap almost completely. "Highest logit wins" aggregation means one block's mask dominates.

**Problem 7:** SAM produces masks smaller than actual block extent. Mode B "template gate" gets mIoU 0.204 vs Mode A "SAM mask" at 0.188 -- confirming SAM underestimates block size.

**Problem 8:** Logit-competition aggregation only assigns labels where SAM masks cover. Any uncovered pixel stays label_map=0 (background). Unlike geometric methods that tile the circumference, SAM leaves gaps.

**Problem 9:** `project_back_to_point_cloud` line 535 uses `valid_update_mask = np.isin(pred[...], [0, 7])`, locking out previously-labeled points.

### Conclusion

Problem 1 is the showstopper: SAM's vision model cannot reliably segment tunnel blocks from depth maps. Problems 2-8 are fixable in code but won't overcome the fundamental SAM limitation. This is why geometric methods (0.77+ mIoU) massively outperform SAM (0.19 mIoU) even with identical GT positions.

**Decision:** Defer SAM improvements; focus on geometric segmentation pipeline for production use.

## Geometric Per-Instance Improvements (hull + mask modes)

Added convex hull and GT pixel mask modes to `p4tun/4-2_geo_per_instance.py`.

### Results with GT Segments (all_segments_gt.csv)

### Results with Detected Centres (all_segments.csv)

| Mode | Shrink | mIoU | Notes |
|------|--------|------|-------|
| bbox | 4/2 | **0.453** | Original baseline |
| hull | 0 | **0.469** | +0.016 from hull shapes |
| hull | 1 | **0.467** | Similar; detection accuracy is the bottleneck |

**Important:** These runs still **require GT**. Per-instance hull/bbox shapes are always computed from `enhanced.csv` (segment labels), `pixel_to_point.pkl`, and `all_segments_gt.csv`. Only the segment centres (X, Y) come from `all_segments.csv`. So 0.467 is "detected centres + GT-derived shapes", not a fully GT-free pipeline. For a new tunnel without any GT, use per-type geometric (e.g. `4-2_geo_segmentation_template.py`) instead.

### Key Findings

1. **GT ceiling is 0.993 mIoU** (mask mode), proving the pixel-mapping path can deliver near-perfect segmentation with perfect centres.
2. **Convex hulls improve GT by +0.12 mIoU** (0.770 to 0.889) by fitting block shapes more tightly and automatically handling trapezoids and compressed rings.
3. **Remaining hull gap (0.889 to 0.993)** is from convex hulls including inter-block groove regions (BG false positives). The mask mode bypasses this entirely.
4. **With detected centres, hulls give modest +0.016** improvement. Detection accuracy (centre errors ~900+ px for some rings) dominates segmentation quality. **Shapes still come from GT**; only placement uses detected centres.
5. **Ring 124 (ring 5) requires pixel mask fallback** -- blocks are too compressed for convex hulls. Auto-detected via median hull Y-range > height/3.
