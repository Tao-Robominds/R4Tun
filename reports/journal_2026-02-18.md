## Experiments & Results (chronological)

### 1. Midpoint Boundary Assignment with K_height Constraint

**Idea:** For each ring, compute block Y boundaries as midpoints between adjacent block centres. Exception: K-block uses physical `K_height = 1079.92 mm` (half-height = 108 px). `groove_shrink = 5 px` on each boundary.

**Result: mIoU = 0.655**

```
BG=0.489  K=0.522  B1=0.795  A1=0.711  A2=0.617  A3=0.652  A4=0.711  B2=0.747
```

**Problem:** Midpoint boundaries assume all blocks are the same size. They are NOT. In complex staggered tunnels, blocks have vastly different angular extents due to ring rotation.

### 2. Groove Shrink Sweep (midpoint boundaries)

Swept `groove_shrink` from 5 to 60 px. **Performance monotonically decreased** with larger shrink:

```
gs= 5px  → mIoU=0.651
gs=60px  → mIoU=0.458
```

**Insight:** The midpoint boundaries are already SMALLER than the actual blocks for most segments. Shrinking further only removes correctly-assigned pixels. The real fix is to use correct per-block heights, not bigger grooves.

### 3. Discovery: GT Per-Block Extents Are Wildly Different

Computed actual GT pixel extents per block by mapping GT labels → pixel coordinates:

**Ring 0 example (Y extents):**

| Block | GT Y range | Extent (px) | Extent (mm) | Det. centre offset |
|-------|-----------|-------------|-------------|-------------------|
| A3 | [65, 150] | 85 | 425 | -5 px |
| A4 | [151, 889] | 738 | 3690 | +89 px |
| B2 | [893, 1655] | 762 | 3810 | +37 px |
| K | [1610, 1906] | 296 | 1480 | +3 px |
| B1 | [1859, 2628] | 769 | 3845 | +42 px |
| A1 | [2629, 3372] | 743 | 3715 | -26 px |
| A2 | [3376, 3458] | 82 | 410 | -3 px |

**Key observations:**
- A2 and A3 are tiny (82–85 px) because they sit at the image wrap boundary (top/bottom of the cylindrical projection).
- B blocks are the largest (~760–770 px).
- K GT extent (296 px = 1480 mm) is larger than declared `K_height = 1079.92 mm` — GT includes boundary-adjacent points.
- Detected centres can be **up to 119 px off** from GT centres (Ring 4, B2).
- Different rings have completely different block proportions due to the staggered rotation.
- All blocks in a ring tile the full circumference: sum of extents ≈ image height (3469 px).

### 4. Theoretical Upper Bound: Direct GT Label Projection

Painted each 3D point's GT label onto its projected pixel, then read back via `pixel_to_point`.

**Result: mIoU = 0.925**

```
BG=0.830  K=0.826  B1=0.976  A1=0.946  A2=0.982  A3=0.966  A4=0.944  B2=0.927
```

This is the ceiling for any pixel-based approach. Not 1.0 because:
- Multiple 3D points map to the same pixel (last-write-wins conflicts)
- Only 9.4% of image pixels have GT point projections (831,959 / 8,828,605)
- Some background points project to pixels that also have segment points

### 5. GT Per-Block Y Extents + Midpoint X Boundaries

Used actual GT Y extents per block, but still midpoint-based X boundaries between ring centres.

**Result: mIoU = 0.758**

```
BG=0.522  K=0.554  B1=0.832  A1=0.850  A2=0.857  A3=0.836  A4=0.844  B2=0.771
```

**Improvement:** +0.103 over midpoint boundaries. Confirms per-block heights matter enormously.

### 6. GT Per-Block XY Extents + Distance Conflict Resolution

Used actual GT XY bounding boxes per block. For overlapping regions (adjacent blocks' bounding boxes overlap), assigned pixel to the block whose centre is closest (Euclidean distance with wrap-awareness).

**Result: mIoU = 0.793**

```
BG=0.533  K=0.615  B1=0.866  A1=0.871  A2=0.896  A3=0.874  A4=0.877  B2=0.813
```

**Improvement:** +0.035 from using per-block X extents instead of midpoint X. Distance-based conflict resolution handles the B2/K and B1/K overlaps.

**Confusion analysis (top errors):**

| GT | Predicted | Count | Cause |
|----|-----------|-------|-------|
| BG → B2 | 19,692 | Bounding box includes groove pixels |
| BG → B1 | 19,434 | Same |
| BG → A1 | 16,962 | Same |
| BG → K | 15,597 | Same |
| B2 → BG | 13,740 | Block extends beyond bounding box |
| K → BG | 13,049 | K bounding box too small |

### 7. Asymmetric Bounding Box Shrink

Swept X-shrink (sx) and Y-shrink (sy) independently:

```
sx=4 sy=2 → mIoU = 0.8048  ← BEST
sx=4 sy=0 → mIoU = 0.8032
sx=6 sy=2 → mIoU = 0.8017
sx=0 sy=0 → mIoU = 0.7931
```

**Optimal: sx=4, sy=2** — shrink X boundaries by 4 px and Y by 2 px each side.

**Result: mIoU = 0.805** (saved to `final.csv`)

```
BG=0.569  K=0.625  B1=0.873  A1=0.876  A2=0.901  A3=0.885  A4=0.883  B2=0.827
```

### 8. Staggering Angle (Parallelogram) — Failed

Tried applying the `angle_deg = 7.52°` staggering angle to create parallelogram boundaries instead of rectangles. X boundaries shift with Y position.

**Result: mIoU = 0.739** (WORSE than rectangular)

The pixel-by-pixel loop implementation may have had issues, or the angle doesn't apply in the depth-map projection the way expected. Rectangles work better.

### 9. GT Label Propagation with Distance Limit

Started from direct GT pixel labels (0.925 mIoU) and propagated to fill empty pixels using nearest-segment distance transform:

```
max_dist= 0 → mIoU = 0.925  (no fill, GT pixels only)
max_dist= 3 → mIoU = 0.881
max_dist= 5 → mIoU = 0.852
max_dist=10 → mIoU = 0.819
max_dist=20 → mIoU = 0.806
max_dist=30 → mIoU = 0.804
```

**Insight:** Every pixel of propagation HURTS. The 90.6% of empty pixels are mostly background (grooves, tunnel surface). Filling them with segment labels adds false positives. The 0.925 is achievable only because the evaluation counts empty pixels as correctly-unassigned background.

## Key Insights

1. **Block sizes vary enormously** within and across rings. In Ring 0, A2 is 82 px while B1 is 769 px — a 9.4x difference. There is no single "A_height" or "B_height" that works. Each block in each ring has its own extent.

2. **Midpoint boundaries are fundamentally wrong** for complex staggered tunnels. They assume equal-sized blocks and systematically under-size small blocks while over-sizing large ones.

3. **The gap from 0.805 to 0.925 is the "rectangle vs. reality" gap.** Real block shapes in the depth map are not perfect rectangles. They have irregular edges from the point cloud projection, and the grooves between blocks are narrow irregular strips. Rectangular bounding boxes can't capture this.

4. **Per-block extents are the most impactful tunable.** Going from midpoint (0.655) to GT per-block XY (0.793) gave +0.138 mIoU — the single biggest improvement.

5. **Ring X boundaries matter less** than block Y boundaries. Per-ring X extent vs per-block X extent only gave +0.035.

6. **Detected centres have significant offsets** from GT centres (up to 119 px / 595 mm). This means when using drifted detections, the bounding boxes will shift and performance will drop.

7. **Ring-to-GT mapping:** Detected Ring i = GT Ring (107 + i). Ring 3 is missing K and B1; Ring 1 is missing A4; Ring 5 is missing A3.

8. **Missing blocks are a sub-section edge effect, not a detection failure.** The GT also has the same missing blocks. Point density varies 18x across rings (Ring 0: 30K pts, Ring 6: 534K pts) — the scanner is near Ring 6. Edge rings (0, 1) have very sparse data (A2 has only 445 pts in Ring 0). Ring 3's missing K and B1 is mid-scan, likely an occlusion or GT labeling gap. **For cleaner evaluation, consider using a sub-section where all 7 blocks are present in every ring, or at minimum evaluate per-ring to isolate edge effects.** Ring 6 (all 7 blocks, 534K pts) and Ring 4 (all 7 blocks, 159K pts) are the most reliable rings in the current data.

## Tunable Parameters for BO (extracted 19 Feb)

### Final Parameterisation: 10 parameters

The geometric script (`3_geometric.py`) is now parameterised with **10 BO-tunable parameters** stored in `parameters_geometric.json`:

| # | Parameter | Current Value | Unit | Description |
|---|-----------|:------------:|------|-------------|
| 1 | `K_half_height` | 153 | px | Half-height of K block (from centre to Y boundary) |
| 2 | `B1_half_height` | 418 | px | Half-height of B1 block |
| 3 | `B2_half_height` | 377 | px | Half-height of B2 block |
| 4 | `A1_half_height` | 351 | px | Half-height of A1 block |
| 5 | `A2_half_height` | 371 | px | Half-height of A2 block |
| 6 | `A3_half_height` | 380 | px | Half-height of A3 block |
| 7 | `A4_half_height` | 377 | px | Half-height of A4 block |
| 8 | `segment_half_width` | 197 | px | Half-width of ring (X direction) |
| 9 | `shrink_x` | 4 | px | X boundary inset (groove margin) |
| 10 | `shrink_y` | 2 | px | Y boundary inset (groove margin) |

### How values were derived

- **Block half-heights**: Mean of max(centre-to-top, centre-to-bottom) across non-wrapping instances (GT extent > 200px). Computed from GT segment labels projected to pixel coordinates.
- **segment_half_width**: Mean of per-ring half-widths (ring centre to X boundary of GT labels). Range: 186–214px, mean 197px.
- **shrink_x/y**: Optimal values from asymmetric sweep on GT bounding boxes. Sweep tested sx ∈ {0–6}, sy ∈ {0–6}; best at sx=4, sy=2.

### Performance with this parameterisation

| Segments Source | mIoU | Notes |
|----------------|------|-------|
| GT (`all_segments.csv`) | **0.659** | Per-type half-heights + detected centres |
| GT with per-instance bounding boxes | **0.805** | The ceiling for rectangular geometry |
| GT label pixel projection | **0.925** | Theoretical upper bound |

### Why 0.659, not 0.805?

The 0.146 gap from 0.659 to 0.805 comes from **detected centre offsets**:
- Detected centres can be up to **119 px off** from GT block centres
- Per-type half-heights are symmetric around the detected centre
- With a 100px centre offset, one side of the box extends too far (into neighbour) while the other side is too short (misses block pixels)
- Per-instance GT bounding boxes capture the actual asymmetric extent

**Alternative parameterisations tested and rejected:**
1. **Half-height scaling** (×1.0–2.0): A-block IoUs didn't change — larger boxes just extend into Voronoi territory. K and B IoUs decreased. Best: scale=1.0.
2. **Weighted midpoint boundaries** (proportional to block-type extents): 0.666, minimal improvement over simple midpoint (0.655).
3. **Walk-from-K model** (derive all boundaries from K position + cumulative extents): 0.504, much WORSE — cumulative error propagates to distant blocks (A2=0.17, A3=0.10).

### Conclusion on tunability

The **centre offset is the bottleneck**, not the block extents. BO can optimise the 10 geometric parameters, but the ceiling with detected centres is ~0.66. Closing the gap to 0.80+ requires either:
1. **Better centre detection** (reduce drift)
2. **SAM boundary correction** (use image evidence to shift boundaries)
3. **Per-instance offset parameters** (too many for BO)

**SAM's role is now clear**: correct the ~0.15 mIoU gap caused by centre offsets, using depth map evidence to refine geometric boundaries.

## Reflection

Today was a breakthrough day. We went from 0.518 (SAM-only) to 0.805 (geometric with GT per-instance bounding boxes), a **+0.287 mIoU improvement**. The key unlock was abandoning the assumption that all blocks are the same size and instead using per-block GT extents.

The most surprising finding was how different the block sizes are — A2 at 82 px vs B1 at 769 px in the same ring. This makes midpoint-based boundaries fundamentally wrong and explains why all previous approaches struggled.

The parameterised geometric approach (10 BO-tunable parameters) achieves **0.659 mIoU** — the gap to 0.805 is caused by detected centre offsets (up to 119px), which no amount of per-type parameter tuning can fix. The theoretical ceiling of 0.925 from direct GT label projection shows the remaining room.

**Key insight for tomorrow**: SAM's value is NOT in overall segmentation (it only got 0.518 alone) but specifically in **correcting the centre-offset boundary errors** that limit the geometric approach. The geometric structure provides the framework (which blocks exist where), and SAM provides the pixel-level boundary refinement.

Tomorrow's critical question: how much does the 0.659 drop when we switch to drifted detections (additional ~248px drift on top of existing centre offsets), and can SAM recover that loss?
